# AI Sales Platform — постоянные инструкции

MVP консультанта для сайтов российских застройщиков. Первая контрольная точка: свободный диалог покупателя → реальные квартиры и ответы по источникам → явное согласие и подтверждение → заявка с историей в тестовой CRM. Затем кабинет риелтора, фиксация и изолированная демонстрационная бронь.

## Начало работы в новом чате

1. Прочитать `docs/CURRENT_STATE.md`, `docs/DECISIONS.md` и нужный этап `docs/ROADMAP.md`. Архитектура — `docs/ARCHITECTURE.md`, запуск — `README.md`.
2. Проверить `git status --short`, изучить затрагиваемый код и тесты. Незакоммиченные изменения пользователя сохранять; не выполнять автоматический сброс данных.
3. Выполнять только согласованный спринт или подэтап небольшими последовательными изменениями. Не считать дорожную карту поручением реализовать всё сразу.

## Постоянные ограничения

- Объяснять изменения на русском; использовать существующие модели и сервисы, не переписывать рабочий код без необходимости.
- Django отвечает за бизнес-правила, валидацию, доступ и БД. LLM понимает запросы и формулирует ответы; операции выполняет сервер.
- Единственный целевой режим чата — свободный диалог. Не развивать дерево шагов, обязательную анкету и переключатель scenario/free. Старые диалоги переводить без потери пожеланий и контактов; старые обработчики удалять после проверки замены.
- Подсказки — обычные сообщения. Карточки, выбор, согласие и подтверждение допустимы как элементы интерфейса. Согласие и отправка заявки требуют явных действий пользователя; модель не подтверждает их за человека.
- Различать обязательные ограничения и пожелания; не ослаблять обязательные фильтры без согласия и не требовать полной анкеты до поиска.
- Один LLMClient и один выбранный адаптер. Ограничивать историю и вызовы; не держать транзакцию БД во время сетевого запроса. При сбое — понятное сообщение и форма контакта, без резервного сценарного движка.
- Каталог MVP: Domoplaner, проект 1368, ЖК «Сибиряков». Сохранять иерархию Developer → ResidentialComplex → ConstructionStage → Building → Section → Floor → Apartment и общий поиск `apps/catalog/search.py`.
- Не придумывать цены, наличие, отделку, условия и сроки. Показывать актуальность синхронизации. Старый снимок — только для разработки и тестов; вымышленные материалы «Кедрового берега» исключены. Источники — по `docs/sprint0/sources.json`, без рекурсивной загрузки Documents.
- CRM тестовая. Реальным квартирам без API бронирования — только запрос менеджеру. Учебная бронь — исключительно на изолированных тестовых объектах; тестовые сроки не выдавать за правила застройщика.
- Учитывать застройщика и аудиторию данных; первая версия — один реальный ЖК. Изоляцию проверять отдельными фикстурами.
- Изменение схемы требует объяснения и миграции. Проверки запускать через изолированную PostgreSQL (`config.settings_checks`); не мигрировать и не импортировать рабочую БД автоматически.
- Не раскрывать `.env`, приватные URL фидов и контакты клиентов в выводе или логах.

## Завершение этапа

Указать изменённые файлы, команды и фактические результаты проверок, ограничения и оставшиеся задачи. Обновить CURRENT_STATE и ROADMAP, новые подтверждённые решения — DECISIONS. Наличие модели/заготовки не означает готовность сценария. При передаче в новый чат указать один следующий подэтап и его критерии готовности.
